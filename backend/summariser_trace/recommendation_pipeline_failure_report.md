# Recommendation pipeline: compact failure report

## Bottom line

The Terraform trace shows a successful summariser request returning `NO_SDG_SIGNAL` for a general-purpose infrastructure tool. That is a plausible result under the current prompt, not a Groq or parser failure. It does **not** show that the end-to-end recommendation was correct: this trace ends at `summarize_for_sdg`; it contains no downstream classifier scores, route response, or UI rendering.

The largest correctness risk is downstream of the trace: on the ST URL path, the recommendation assessor is not just explanatory. Its `relevant` boolean gates whether the classifier runs. Yet that boolean comes from a 20-word check and a small English keyword list, while the embedding check embeds only the user description—not the summary that helped trigger the check. It can therefore suppress valid classification or allow classification on a weak fallback. When no prediction survives, the recommendations are generic because the system selects from a few fixed reason templates; it does not identify which project-specific evidence is missing.

## Trace-specific reading

- **Observed:** Groq returned HTTP 200, `finish_reason=stop`, and the exact sentinel `NO_SDG_SIGNAL`; `_validate_output` deliberately passes that sentinel through. The prompt says not to infer a domain contribution from generic infrastructure being usable in many sectors, so Terraform's result is consistent with the configured policy.
- **Not established by this trace:** that the API route returned no predictions, that the recommendation assessor selected a particular reason, or that the user saw this trace's output. Those require downstream route/classifier/UI evidence.
- **Trace/source drift:** the trace records a 60-second request timeout, but the current `summarize_for_sdg()` default in [summariser.py](../services/summariser.py) is 30 seconds and the shown caller does not pass a timeout. The trace's system-prompt hash and model identify its captured request, but do not prove every detail matches the current checkout.
- **Policy trade-off:** the anti-speculation rule reduces false positive sector attribution, but can erase indirect/enabling contributions of general-purpose infrastructure. The current output offers no “possible enabling role” or uncertainty state; it collapses to a sentinel.

## Failure and missed-edge-case map

| Stage / case | Failure or blind spot | What happens / why it matters |
|---|---|---|
| **ST pre-classifier gate** | Short, jargon-heavy, or unrecognized text can fail `assess_relevance()` before inference. | `/api/classify_st_url` returns `predictions: []` without calling `classify_fetched_repo` when `rec["relevant"]` is false. A missing keyword is treated as evidence to skip the classifier, even though the classifier might have produced a useful score. This is a false-negative path, not merely a diagnostic. |
| **Route / frontend bypasses** | Missing required description is a 400; a missing repository URL returns an empty ST result early without a recommendation; fetch/classifier errors return errors, not guidance. | These cases never reach the ordinary recommendation UI. The frontend prefers a successful ST response, even if it has no predictions, rather than substituting a potentially different Aurora result. Aurora's recommendation normally assesses only the submitted description because the current Aurora response does not include `project_description`. |
| **Sentinel / fallback text** | `NO_SDG_SIGNAL` is a non-empty string, not a typed “no evidence” result. On summariser API failure, the fallback is name + description + topics + a human-readable failure reason, not an SDG-ready summary. | The route assesses that string alongside the user's description, then may pass it to the classifier if the gate is true. Topic words or the user's own keywords can trigger relevance while the actual classifier input remains a sentinel or degraded fallback. No explicit source/quality flag distinguishes generated summary, fallback, and sentinel. |
| **Two text sources, one embedding** | Combined text is used for length and keyword checks, but `_encode_text_chunks()` embeds only `user_description`. | A signal appearing only in the summary can pass the keyword gate while the similarity is computed against an empty or irrelevant user description. Conversely, a precise README summary cannot rescue a poor or absent user description's embedding. This makes the reason and nearest-SDG score internally inconsistent with the evidence that triggered them. |
| **README coverage** | The summariser receives only the first 12,000 cleaned README characters; README assessment separately sees at most 500 cleaned words. | Relevant impact information later in long READMEs is omitted. First-page badges/navigation or setup content can consume the budget. Cleaning removes URLs, HTML, images, and code fences; useful context encoded in those structures may disappear. The assessor never examines the full README as evidence. |
| **Length rule** | Fewer than 20 whitespace-separated words immediately means `text_too_short`, before signal checks. | Strong but concise evidence (“Open clinics share patient records in rural areas”) can be dismissed; repeated/boilerplate words can pass without adding evidence. Description and summary duplication is removed only when the entire normalized description is a substring of the normalized summary; partial overlap or paraphrases inflate the count. URLs are removed, but punctuation, headings, and non-English tokenization still affect the count. |
| **Keyword rules** | A short, fixed, English list uses word boundaries, has no negation/context handling, and short-circuits in a fixed order. | “No health impact” or quoted/example text can trigger a domain signal; the generic word “goal” triggers the SDG-mention branch. Valid topics such as disability, housing, poverty, biodiversity, labor, peace, or digital inclusion can be missed unless another listed term appears. Non-English text, spelling variants, synonyms, and domain-specific phrasing are not handled. The technical scan runs only after no earlier keyword matched, so technical wording can mask no signal but a single broad domain word prevents the technical diagnosis. |
| **Technical-text ratio** | The implementation counts each of 14 technical terms at most once, then divides by all whitespace-separated words; it is not a proportion of technical tokens. The cutoff is strictly `> 0.4`. | Repeated jargon does not increase the numerator, while short descriptions can cross the cutoff abruptly. Technical terms in a long README/summary can be diluted by unrelated prose. “Heavily technical” is unavailable whenever any earlier signal matched. |
| **Embedding decision** | The assessor compares chunk embeddings to 17 SDG descriptions and uses the maximum chunk similarity; the hard boundary is strict `> 0.25`. | A single incidental chunk can dominate; the score does not establish project impact or classifier confidence. There is no calibration against the classifier's model, route cutoff, or observed false positives. `threshold_too_high` is inferred from this independent 0.25 rule, not from the classifier threshold. In the ST classifier, scores are retained at `>= 0.3`; Aurora retains only `> 0.4`, so a recommendation cannot reliably diagnose why either route filtered a result. |
| **Chunking/runtime** | Tokenizer/model loading and encoding are synchronous and exceptions are not handled inside `assess_relevance()`. | Model download/load failures, invalid tokenizer limits, malformed embedding shapes, or inference errors propagate to the route's generic 500 handler. The 500-word README cap limits one path, but the combined summary/description passed to the assessor has no local size cap. Each SDG takes its best chunk score, so an incidental chunk can dominate; exact SDG-score ties resolve to the first SDG through `argmax`. There is no score margin or ambiguity reporting for close SDGs. |
| **Summariser output validation** | `_validate_output()` accepts any non-sentinel output with at least 10 words, and truncates only outputs over 200 words. It does not enforce the prompt's 80–160 words, 4–6 sentences, English, non-speculation, or “no SDG names” requirements. | Format/prompt violations, unsupported claims, wrong-language output, and subtle instruction-following failures can reach the classifier. Repository README text is untrusted input; prompt instructions alone do not guarantee that embedded instructions or misleading claims are ignored. |
| **Groq response shape** | The caller handles timeout/request/HTTP errors and `KeyError`/`IndexError`, but not every malformed JSON shape or wrong field type. | A valid JSON list/null, non-dict `message`, or non-string `content` can raise `AttributeError`/`TypeError` instead of returning the fallback; the route then fails rather than producing a recommendation. There is no retry/backoff. Many ordinary API failures instead return the metadata fallback, which can look like usable classifier text despite not being a generated impact summary. |
| **Recommendation/UI** | The API returns a reason category and canned suggestions, not a diagnosis tied to text spans or project facts. | “Add beneficiaries/context/impact” repeats across cases and does not say what this repository already establishes or what specific evidence is missing. `nearest_sdg` is only a single coarse candidate; the UI can choose the higher similarity from the separate user-description and README assessments, but shows the ordinary recommendation's suggestions, not the README assessment's. Users may see a closest candidate disconnected from the guidance. `text_quality` is not a calibrated confidence and is not shown. |
| **Coverage / documentation** | Tests cover selected boundaries, the sentinel happy path, cache reuse, and route gating; they do not exercise the failure combinations above. | There are no direct quality tests for keyword coverage, multilingual text, negation, chunk aggregation, summary fallbacks, malformed provider payloads, or whether recommendations improve after adding concrete evidence. The existing [recommendation_pipeline.md](../../docs/recommendation_pipeline.md) is partly stale: it says the technical cutoff is `> 0.5`, says the low-similarity quality is unclamped, and lists an “increase threshold” suggestion not returned by current code (actual cutoff `> 0.4`; `_bounded_quality()` clamps). |

## Why the recommendations are generic

1. **Only five fixed reasons:** every input within a branch gets the same suggestion list, regardless of the words or repository.
2. **No evidence extraction:** it does not identify which problem, beneficiary, geography, outcome, or domain was actually found or absent.
3. **No grounded explanation:** suggestions have no quoted README/description evidence, source attribution, or distinction between “not mentioned” and “not fetched.”
4. **Nearest SDG is not a recommendation plan:** it is the maximum embedding match, not a ranked, calibrated diagnosis; the code does not translate it into SDG-specific evidence prompts.
5. **No feedback loop:** the app does not ask targeted follow-up questions, let the user amend one missing field, or compare a revised description against the old assessment.

## Improvement scopes, in priority order

1. **Correctness boundary (highest priority):** make relevance assessment diagnostic-only, or explicitly separate a conservative classifier gate from recommendation generation. Never infer “no SDG” solely from absence in the current keyword list. Pass typed summary state (`generated`, `fallback`, `no_signal`, `unavailable`) rather than magic text; avoid classifying the sentinel or failure explanation as project content.
2. **Evidence-consistent assessment:** score the same normalized evidence that triggered the check. Keep description, generated summary, metadata, and README excerpt distinct with source/quality labels; combine or compare their embeddings deliberately. Return evidence spans and explain uncertainty rather than one unlabeled nearest score.
3. **Specific, actionable guidance:** map detected evidence to a structured gap list (problem, affected people, setting, outcome, project role). Generate prompts such as “Your README describes clinic record sharing but names no patient group or care outcome,” only when supported by cited text; otherwise ask a neutral targeted question. Keep an explicit no-evidence state rather than fabricating an impact claim.
4. **Robust summariser contract:** validate response types and semantic constraints; bound/cap all inputs; handle provider shape/content errors through an explicit failure result; test adversarial README instructions, truncation, empty repositories, non-English text, fallback topics, and valid short descriptions. Preserve the no-speculation policy, but consider a separately labeled “enabling infrastructure / indirect contribution” path if maintainers want those projects represented.
5. **Calibrate and measure:** build a small reviewed set of positive, negative, borderline, indirect-impact, and low-documentation repositories. Measure gate false negatives, classifier precision/recall, reason accuracy, recommendation usefulness, and source attribution. Tune any threshold against that set—not the unrelated fixed 0.25 similarity rule.
6. **Align product and documentation:** show which source produced the closest signal; distinguish “no score passed the classifier cutoff” from “no contribution”; update [recommendation_pipeline.md](../../docs/recommendation_pipeline.md) and frontend guidance when the contract changes.

## Architecture trade-off: make README assessment a separate API?

### Current behavior

`/api/classify_st_url` already performs two logically separate assessments in one request: it assesses the submitted description plus summariser output (`rec`), then assesses the README excerpt alone (`readme_assessment`). It returns the latter to the client, but **does not use its result to gate or alter ST classifier predictions**. Only `rec["relevant"]` gates `classify_fetched_repo()`. Thus the README assessment is separate as data, but not yet part of the ST decision.

### Pros of separating the responsibility

- Makes README evidence independently inspectable and easier to test, tune, or reuse without mixing it with user-written description/summary text.
- Could let the ST route combine source-specific evidence deliberately, helping when repository metadata is poor but the README documents real impact.
- Gives clients a reusable README-only diagnostic if they need it for a separate UI, workflow, or future batch analysis.
- Can isolate future expensive processing (for example, large-document extraction) if measured latency or scaling needs justify it.

### Cons and failure risks

- A separate HTTP endpoint called by the ST route adds a network/serialization hop, latency, timeout and error behavior, and another contract/version to maintain. If both handlers run in this Flask process, this is avoidable overhead; an internal service function is the simpler boundary.
- The current README result is not an independent oracle: it uses the same keyword rules, embedding model, and fixed `> 0.25` similarity boundary. Calling it separately does not inherently improve precision or explainability.
- Combining two `relevant` booleans with OR can turn a weak keyword hit in either source into a classifier run; AND can suppress valid evidence found in only one source. Taking the larger similarity can over-weight boilerplate or one accidental chunk. The current `nearest_similarity` is a heuristic similarity, **not** an ST classifier score or calibrated confidence.
- The README excerpt is capped at 500 words and may contain setup/technical text; a separate endpoint does not solve truncation, missing context, language coverage, or the inaccurate length/keyword heuristics.
- If the endpoint becomes a required internal dependency, its outage can fail the main ST request unless failure behavior is explicitly defined. Re-fetching or re-cleaning repository content in both handlers could also duplicate work and create inconsistent snapshots.
- A new endpoint expands the public/API surface and may encourage clients to treat the diagnostic as a definitive project-impact judgment.

### Is the trade-off worth it?

**Separate the logic, not necessarily the network API.** For the current app, a dedicated internal README-assessment function/service and an explicit, tested combination policy are likely beneficial; a second HTTP endpoint that `/api/classify_st_url` calls is **not worth the added complexity yet**. The current code already computes and returns README-only assessment in the ST response. First decide whether it should influence classification at all; today it is display-only.

If README evidence is meant to affect the ST result, do not simply OR `relevant` or take the highest similarity. Keep source-level results distinct, combine them through a calibrated rule (or use them only as diagnostics), record which source supported the decision, and ensure the summariser sentinel/fallback is never scored as ordinary project text. Compare gate false negatives and classifier precision/recall on a reviewed repository set before making the README signal authoritative.

A standalone HTTP API becomes worthwhile only if README assessment has independent consumers, needs separate deployment/scaling, or must be invoked asynchronously/by external clients. Even then, the ST path should call a shared internal service/client boundary with explicit timeout and fallback behavior—not make an in-process HTTP call back into itself. A separate API endpoint is not the same as a separate microservice.

### Planning checklist (no implementation performed)

1. Specify the output contract: per-source relevance, nearest candidate/similarity, evidence and source quality; clearly label heuristic values as uncalibrated.
2. Decide whether README assessment is advisory-only or participates in the ST classifier gate; define missing, empty, sentinel, and failed-assessment behavior.
3. Evaluate candidate combine policies on labeled repositories; reject a policy that improves recall only by materially increasing false positives.
4. Only if independent consumers or operational scaling require it, expose a separate HTTP endpoint; otherwise retain one route and separate the internal logic.
